S-3: PID Record Parsing into an FDO record

This step takes an identifier record from [Step 2] and MUST convert it into a set of type value pairs.
Inputs
This step expects exactly one syntactically valid PID record in the format of choosing of the PID system. This input MUST NOT be blank. Typically, this is the output of .
Outputs
The result of this step is an unvalidated FDO record with all type-value pair tuples parsed out of the PID Record. At this point, the information inside the tuples is not yet validated against the attribute definitions and profiles. The structure of the FDO record MUST be valid. Typically, this FDO record structure consists out of the following information:
  • The PID the FDO record was resolved with.
  • A list of FDO attribute tuples. The first value in every tuple refers to the attribute definition AKA type of the type-value tuple. The second value in every tuple is a value claiming to be compliant to this attribute definition or stated differently, an instance of the type.

Any other information extracted from theFDO record such as intrinsic metadata, are not requirements of the specification but will be described within the respective implementation profile. Examples such as the record, tuple time stamps of resolution in [[!RFC3339]] format, a time to live (TTL), and possibly other implementation-specific fields.

Expected behavior
This step SHALL transform a PID record into an unvalidated FDO record. This step MUST terminate within a reasonable minimal timeframe (e.g., of < 10 ms) and if it needs to issue network requests, it MUST implement information caching solutions for efficiency purposes. If needed, some PID system-specific information MAY be transformed into FDO attributes.
